Data Model Harmonization Relay

Goals

Your team has been handed data models from multiple research consortia. They overlap, they use different terminology, and they don’t always agree.

Your challenge: harmonize them into one reusable, ontology-aligned model before the other teams do.

This workshop is a relay race in four legs. Each teammate runs one leg, then passes the baton to the next teammate. The baton is a saved copy of the project plus a handoff comment.

You’ll use the CoreModels MCP and Synapse MCP to search existing models, compare standards, reuse what already exists, resolve differences, and validate the final model.

What you need

The relay

🏆 Finish line

Present your team’s harmonized model and explain:

  • What you reused
  • What you changed
  • Which conflicts you resolved
  • Which ontologies you aligned to
  • What validation issues you found
  • Where gaps still remain

Bonus challenge: Can your team finish with the fewest new fields while still meeting all of the requirements?

The legs

🏁 Leg 1

Discover Data Models

Find every existing model for the assay, work out which fields describe the same concept, and draft one common model. Leg 1 decides the concepts. Value lists belong to Leg 2 and ontology terms to Leg 3.

Setup. The facilitator creates a working project for each team as a live child of the source project. Your team picks any assay or data type that already has templates there.

Steps
0
Set the context (fill in once)
Prompt · fill in the brackets

My working project in CoreModels is "[project name]" and the assay or data type I am modelling is "[assay or data type]". Remember both for this conversation. Everything below refers to them.

1
Find the existing models
Prompt

In my working project, list every Type that relates to the assay or data type I named. Treat variants of it separately. For each Type, tell me how many fields it has and which consortium or program it seems to come from. Then use the Synapse MCP to check whether any consortium has a registered schema for this assay that is missing from the list.

2
Compare the fields
Prompt

For the Types you just found, list every field with its label. Group fields that describe the same concept even when their names differ, for example because of different prefixes, casing, or wording. Show a table with one row per concept and one column per Type. Flag fields that appear in only one Type, and mark fields that already exist as shared elements we could reuse as they are.

3
Draft the common model
Prompt

Propose one common template for this assay or data type with exactly one term per concept, so a contributor fills in each idea once. Reuse existing elements wherever they fit instead of creating new ones. Use one naming convention with no program prefixes. Organize the fields into logical groups that follow the steps of the workflow, and mark which fields are required. Move fields that are specific to one program, or that describe processed results instead of the original data, into a separate list. Do not write value lists or ontology terms yet.

4
Record the mapping and the doubts
Prompt

Make a table mapping every old field in every source Type to its new term, or to "dropped" or "moved out" with a reason. Then list the merges you are least sure about, where two old fields might mean different things or use different sets of allowed values.

5
Build it and pass the baton
Prompt

In a new space of my project, create a Type named "Common" followed by the assay or data type name (no spaces), with these fields and a description for each. Mark required fields. Then leave a project-level comment titled "Leg 1 handoff" containing the mapping table, the list of reused elements, and the list of uncertain merges. Finally copy the project and name the copy "[assay or data type] - Leg 1 handoff".

Pass the baton to Leg 2

  • The copied project with the draft Common Type and field descriptions
  • The old-to-new mapping table in the "Leg 1 handoff" comment
  • The list of reused elements and the list of uncertain merges

Done when

🧩 Leg 2

Harmonize: resolve and reuse

Take the Leg 1 draft and settle its differences: decide the uncertain merges, agree one definition and data type per field, write value lists, and reuse existing components wherever possible.

Setup. Open the project your teammate handed you and read the "Leg 1 handoff" comment first. Work in a new copy of it named "Leg 2 working".

Steps
0
Set the context (fill in once)
Prompt · fill in the brackets

My working project in CoreModels is "[project name]". A teammate handed it to me. Read the comment titled "Leg 1 handoff" and the Type whose name starts with "Common", and remember them for this conversation. Everything below refers to them.

1
Decide the uncertain merges
Prompt

For each uncertain merge in the Leg 1 handoff, compare the old fields' definitions, data types, and allowed values. Recommend keeping the merge or splitting it, and give the reason. Show the evidence for each recommendation.

2
Agree definitions and data types
Prompt

For every field in the Common Type, compare the descriptions and data types of the old fields it replaces. Propose one definition and one data type for each field, and flag every place where the source models disagree.

3
Write the value lists
Prompt

Which fields in the Common Type should have a fixed list of allowed values, and which should stay free text or numeric? For each list field, propose the values, making sure the list covers every value the merged old fields allowed.

4
Reuse, remove duplicates, find gaps
Prompt

Check whether any field or value list in the Common Type duplicates an element that already exists in the parent project. Where one exists, propose reusing it instead of keeping a new node. Then list any concept the source models need that the Common Type is still missing.

5
Apply the changes and pass the baton
Prompt · list the changes you accepted

Apply only these changes: [list the ones you accepted]. Create the value lists and link them to their fields. For each change, add a comment on the node saying what changed and why. Then leave a project-level comment titled "Leg 2 handoff" listing: merges kept or split with reasons, definitions and data types changed, value lists created, elements reused, and gaps still open. Copy the project and name the copy "[assay or data type] - Leg 2 handoff".

Pass the baton to Leg 3

  • The model with merges decided, one definition and data type per field, and value lists
  • A reason for every change, as comments on the nodes
  • The list of reused elements and open gaps in the "Leg 2 handoff" comment

Done when

🔗 Leg 3

Match to Ontologies

Give the model its meaning by binding fields and values to established ontology terms. Leg 3 owns the bindings. If a match makes you doubt an earlier decision, leave a comment on that node instead of editing it.

Setup. Open the project your teammate handed you and read the "Leg 1 handoff" and "Leg 2 handoff" comments. Work in a new copy named "Leg 3 working".

Steps
0
Set the context (fill in once)
Prompt · fill in the brackets

My working project in CoreModels is "[project name]". A teammate handed it to me. Read the comments titled "Leg 1 handoff" and "Leg 2 handoff" and the Type whose name starts with "Common", and remember them for this conversation. Everything below refers to them.

1
Search ontologies
Prompt

For each field and each value-list value in the Common Type, search public ontologies (for example through the EBI Ontology Lookup Service) for a matching term. For every field or value, show the top candidates with their ID, definition, and source ontology. Say which candidate you would choose and why, and say plainly where nothing matches.

2
Check the matches yourself

Read each definition. A label match is not enough. Ask three questions:

  • Does the definition say the same thing as our field description?
  • Does the ontology belong to this field's community, or is it borrowed from another (for example, one written for a different organism or discipline)?
  • Does the term describe the field, or only one of its values?
3
Bind what you accept
Prompt · list the terms you accepted

Bind only these ontology terms: [list the ones you accepted, with their IDs]. Do not bind anything else. For each binding, add a comment on the node stating why it was chosen and recording the term's IRI.

4
Record gaps and pass the baton
Prompt

Leave a project-level comment titled "Leg 3 handoff" listing: every binding with its reason, every field or value with no ontology match, any binding borrowed from another community, and any place where an ontology match made you doubt an earlier merge. Then copy the project and name the copy "[assay or data type] - Leg 3 handoff".

Pass the baton to Leg 4

  • The model with ontology bindings
  • A reason and IRI for each binding
  • A list of unmatched terms, borrowed terms, and merges that now look wrong

Done when

✅ Leg 4

Validate in Synapse

Put the harmonized model to the test with sample data from every consortium, fix what the tests show is wrong with the model, and prepare the finish-line summary. Every change needs a reason that traces to a failed test.

Setup. Open the project your teammate handed you and read all three handoff comments in order. Work in a new copy named "Leg 4 working". The facilitator may supply one sample manifest per consortium. If there are none, use the generator prompt in Step 1.

Steps
0
Set the context (fill in once)
Prompt · fill in the brackets

My working project in CoreModels is "[project name]". A teammate handed it to me. Read the comments titled "Leg 1 handoff", "Leg 2 handoff", and "Leg 3 handoff" and the Type whose name starts with "Common", and remember them for this conversation. Everything below refers to them.

1
Get test data
Sample generator prompt

For each source Type listed in the Leg 1 handoff mapping, write a realistic sample manifest as CSV with 5 rows, using that Type's original field names. Include two deliberate problems in each: one missing required value and one value outside the expected set. Label which rows are valid and which are not.

2
Translate each manifest with the mapping
Prompt

Using the mapping table in the Leg 1 handoff comment and the changes in the Leg 2 handoff comment, convert each sample manifest into the fields of the Common Type. Show me what happened to every column: mapped cleanly, merged (with the rule used), or dropped. List any value that had no home in the value lists.

3
Validate
Prompt

Export the Common Type as a JSON Schema and read it back to me: field names, types, required list, and allowed values. Then validate each converted row against it. Report per source consortium: rows passed, rows failed, and the reason for each failure.

4
Diagnose failures

Sort each failure into one of these before fixing anything:

  • The test data was wrong (bad row, expected to fail)
  • The mapping was wrong (an old value converted badly)
  • The model was wrong (a field is missing, a list lacks a real value, a required flag is too strict)
5
Fix the model and run the checklist

The Copy button on this prompt includes the full validation checklist below.

Prompt · checklist included on copy

Fix the model failures only. For each change, add a comment on the node saying what changed and which failure it fixed. Then work through this checklist against the project and the three handoff comments. For each item say PASS or FAIL and give the evidence, or say what is missing. [validation checklist below]

6
Prepare the finish line
Prompt

Leave a project-level comment titled "Leg 4 handoff" that summarizes, across all four legs: what we reused, what we changed, which conflicts we resolved, which ontologies we aligned to, what validation found (rows passed of rows tested per consortium), where gaps remain, and how many new fields the model adds compared with reusing existing ones. Then copy the project and name the copy "[assay or data type] - Finish line".
